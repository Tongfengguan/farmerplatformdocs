开发规范与守则 (Engineering Standards) ​

本文档确立了 Farmer Platform 的核心技术原则与代码规范。这是项目保持高内聚、低耦合，以及长期可维护性的基石。在本项目中进行任何修改时，必须绝对服从以下约定。

1. 架构完整性 (Technical Integrity) ​

1.1 纯数据驱动 (Strict Data-Driven) ​

  • 拒绝 Mock 数据: 所有的前端业务数据必须真实地来源于 Spring Boot 提供的 RESTful 接口。项目中曾存在的静态 Mock 数据必须彻底被淘汰，禁止新功能引入任何形式的硬编码业务数据。
  • 状态单一真实源 (Single Source of Truth): 全局的分类、状态码字典（如订单状态、商品分类）统一存放在 src/utils/constants.js 中，或由后端接口统一维护，禁止在组件中硬编码判断。

1.2 外科手术式更新 (Surgical Updates) ​

  • 最小化变更: 无论进行修复还是重构，只触及与任务直接相关的代码逻辑。不要因为“顺手”而去修改周边不相关的格式化或逻辑，除非存在明显致命错误。
  • 清理自己造成的废弃代码 (Orphan Cleanup): 如果您的代码变更导致某些 import、变量或函数不再被调用，您有责任将它们清理干净。

1.3 服务端核心原则 ​

  • 分页优先 (Pagination First): 任何返回列表的 API（如获取商品列表、文章列表、用户列表等），无论数据量大小，必须使用 Spring Data JPA 的 Pageable，并包装在标准化的 PagedResponse<T> 中返回。
  • 规范化响应包装: 所有 API 必须返回包裹了状态码、消息和数据的统一数据结构 ApiResponse<T>。

2. 智能化开发规范 (AI & LLM Integration) ​

基于 DeepSeek 与 LangChain 的 AI Agent 系统需要遵守特定的上下文安全守则。

2.1 安全的上下文管理 (Safe Summary Mode) ​

为了避免大语言模型出现“幻觉”或者输出泄露系统底层 Prompt 的 XML/SML 标签，我们实施了两步安全策略：

  • 步骤 1: 识别用户的意图并触发对应的 Tool Call，调用后端接口获取纯净 JSON 格式的业务数据。
  • 步骤 2: 丢弃并重置对话历史。不将带有繁杂 Tool Call 的内部调用记录给到模型生成最终总结，而是发起一次全新的无状态总结请求。

2.2 结果导向的简洁输出 (Concise Output) ​

AI 的分析报告不能长篇大论。

  • 必须采用要点式（Bullet points）输出，限制在 3-4 个要点。
  • 限制输出字数（约 200 字），直接给出“业务洞察”与“行动建议”。

3. 安全性与拦截器逻辑 (Security) ​

3.1 JWT 无状态认证 ​

  • AuthInterceptor 规范: 所有受保护的接口必须经过 AuthInterceptor 拦截。
  • OPTIONS 放行: AuthInterceptor 必须无条件放行 HTTP 的 OPTIONS 请求（用于 CORS 跨域预检），否则会导致前端跨域报错。
  • 公共白名单: /login, /register, 以及公开查询商品的接口应当被显式放行。

3.2 敏感信息隔离 ​

  • 永远不要将生产环境的真实 JWT Secret、数据库密码提交到代码仓库。开发环境的密钥（如 MySQL 密码 z236244462）仅限本地开发测试使用。

4. Karpathy 指导方针 (Karpathy-Inspired Coding) ​

本项目严格贯彻以下极简与高效开发哲学：

  1. 想清楚再写代码 (Think Before Coding): 遇到模糊的需求，先阐述理解再动手，不要假设用户的意图。如果可以更简单地实现，直接指出。
  2. 简单至上 (Simplicity First): 写出能解决问题的最少代码。不编写推测性的、未经要求的功能（如过度的接口抽象、“万一未来用到”的扩展）。如果花了 200 行解决 50 行就能解决的问题，重写它。
  3. 目标导向 (Goal-Driven Execution): 每一个变更必须有可以被验证的测试目标。无论是 Debug 还是 Feature，执行逻辑应为：重现/明确验证目标 -> 编写代码 -> 验证通过 的独立闭环。
